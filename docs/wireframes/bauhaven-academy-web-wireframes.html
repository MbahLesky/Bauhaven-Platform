"Personal portfolio site" only appears here because Sam was individually granted permission to create their own tasks — most students won't see a create option. The "+ New task" control is hidden entirely without that grant, not disabled: it's an individual override most students don't hold, and a permanently greyed-out button is just a reminder of something they can't do.
Badge colours corrected to match Admin-web. This screen originally had Open as warning and Grading as neutral — the inverse of Admin's, so the same task changed colour depending on which app you opened it in. Admin's reading is the semantically correct one and matches the brand guidelines' colour table: Open is nothing wrong, just work to do (neutral); Grading is waiting on someone (warning); Graded is done (success, carrying the grade itself).
"Draft" was not a real status. tasks.status is open/submitted/graded/archived — a self-created task is simply open. It's distinguished by the "Self-created ·" prefix on its meta line, the same treatment Admin-web's list uses, rather than by a status that doesn't exist.
Submitting is one link, because that's all a submission is. submissions.content_url is the only column carrying the work — there's no file storage and no body text — so a submission points at something hosted elsewhere. The card expands in place rather than navigating to a detail screen: one field doesn't warrant a whole screen transition on a phone.
Submitting moves the task to "submitted" via a database trigger, not via this app — see 006_submission_marks_task_submitted.sql. A student assigned a task can't update it (tasks_update is created_by = auth.uid()), and before that migration nothing performed the transition at all, so Admin-web's Submitted queue would have stayed empty forever.

"Works offline — syncs when you're back online" was removed. Academy-web can't honour it: Bauhaven-Architecture-Plan.md §3 gives web clients best-effort caching and reserves genuine queued writes for the native clients' Drift storage. A web page can't guarantee a queued write ever syncs — the tab closes, the browser evicts storage, there's no durable background sync — and for attendance a false "saved, will sync" is the worst available failure: the student believes they're present and the register disagrees. A failed check-in is a plain error with a retry. The native wireframe keeps the offline promise, because native can keep it.
"Today's session: 9:00am – 1:00pm" was removed. attendance_sessions has session_date only — no start or end time — so those hours aren't representable. Adding time columns is a schema change nobody has asked for.
Three outcomes, not two. Checking in succeeds, finds a record already standing, or is refused by attendance_records_insert (not actively enrolled in the session's program). "Already recorded" is announced as a status rather than an error — nothing failed and nothing was lost. A refusal points at a mentor, who can mark the student present, since Staff bypass the enrolment check.
A session nobody marked shows "Not marked", not "Absent". On a student's own record that distinction matters: being told you were absent when the register was never taken is a different and worse statement, and it's the student who'd have to argue it back.
Excused sessions are left out of the rate's denominator — present ÷ (present + absent). An approved absence is the system saying it doesn't count against you; folding it in would make excusing pointless.

"Goes to your Programme Manager" was corrected to "Goes to staff". "Programme Manager" isn't a role this schema has — users.role is admin/staff/user — and the quorum rule in the Core spec routes a User's request to one Staff approval, not to a named person. Nothing derives a supervisor: users has no such link.
Two date fields, not one "6 Aug – 7 Aug 2026" text box. start_date and end_date are separate date columns, and a free-text range is the field that submits "next week" and stores nothing usable. A single-day absence uses the same date twice.
The badge shows "Waiting", not "Approved". Approval isn't built — and it's blocked in the database, not just missing a screen: requests has SELECT and INSERT policies and no UPDATE, so no row can leave 'pending' by any route. A wireframe showing an approved request implies a state the system currently cannot reach. See the Academy Feature Spec §7, "Requests".
No cancel or edit control, because there couldn't be one. With no UPDATE or DELETE policy, a student cannot withdraw a request they've sent. A button that always failed would be worse than its absence.
Reason is required, though the column is nullable. A request with no reason gives the approver nothing to decide on, and there's no comment thread on requests for them to ask a follow-up through. Rendered as a textarea for the same reason — a one-line box invites a three-word answer.
