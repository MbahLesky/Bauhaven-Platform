Badge colours corrected to match Admin-web. "Works offline — syncs when you're back online" was removed. Academy-web can't honour it: Bauhaven-Architecture-Plan.md §3 gives web clients best-effort caching and reserves genuine queued writes for the native clients' Drift storage. A web page can't guarantee a queued write ever syncs — the tab closes, the browser evicts storage, there's no durable background sync — and for attendance a false "saved, will sync" is the worst available failure: the student believes they're present and the register disagrees. A failed check-in is a plain error with a retry. The native wireframe keeps the offline promise, because native can keep it.
"Today's session: 9:00am – 1:00pm" was removed. attendance_sessions has session_date only — no start or end time — so those hours aren't representable. Adding time columns is a schema change nobody has asked for.
Three outcomes, not two. Checking in succeeds, finds a record already standing, or is refused by attendance_records_insert (not actively enrolled in the session's program). "Already recorded" is announced as a status rather than an error — nothing failed and nothing was lost. A refusal points at a mentor, who can mark the student present, since Staff bypass the enrolment check.
A session nobody marked shows "Not marked", not "Absent". On a student's own record that distinction matters: being told you were absent when the register was never taken is a different and worse statement, and it's the student who'd have to argue it back.
Excused sessions are left out of the rate's denominator — present ÷ (present + absent). An approved absence is the system saying it doesn't count against you; folding it in would make excusing pointless.

The change still stands for the real reason: nothing connects a student to a particular programme manager — user_roles.program_id scopes a staff member to a program, with no reverse lookup and no supervisor link — and the quorum rule routes a User's request to one Staff approval, not to a named person.
Two date fields, not one "6 Aug – 7 Aug 2026" text box. start_date and end_date are separate date columns, and a free-text range is the field that submits "next week" and stores nothing usable. A single-day absence uses the same date twice.
The badge shows "Waiting", not "Approved". A wireframe showing an approved request implies a state the system currently cannot reach. See the Academy Feature Spec §7, "Requests".
No cancel or edit control, because there couldn't be one. With no UPDATE or DELETE policy, a student cannot withdraw a request they've sent. A button that always failed would be worse than its absence.
Reason is required, though the column is nullable. A request with no reason gives the approver nothing to decide on, and there's no comment thread on requests for them to ask a follow-up through. Rendered as a textarea for the same reason — a one-line box invites a three-word answer.

Category is a fixed list, not a text box. issue_reports.category is text not null default 'general' with no check constraint, so free text would put every report in a category of one — unsortable, and useless against the (status, category) index the schema already carries. Nothing upstream enumerates the values, so these five were chosen while building: equipment, program, access, safety, general. The first two mirror the nullable asset_id and program_id columns; general is kept verbatim because it's the column default.
The category is a label, not a destination. The Core spec's "issue reports route to Staff by category" isn't implemented and never was: "category" appears only as that column and that index. issue_reports_select and issue_reports_update both gate on plain auth_is_admin_or_staff() with no category arm, so any Staff member or Admin can read and resolve any report. Corrected in the Core spec.
"Safety or wellbeing" doesn't summon anyone, and the screen says so. It's a category so a Staff member scanning a list can see it without opening rows — but with no routing and no triage screen, telling a student to wait would be wrong. The footer points at a person instead.
Three statuses, not two. The check constraint is ('open','in_progress','resolved'). Academy's row type had it as open | resolved, which would have made a triaged report an impossible value; fixed, and all three render — "Open", "Being looked at", "Resolved".
No triage screen exists anywhere — Admin-web's sidebar has "Issue Reports" with a count badge and its dashboard has an "Open issue reports" stat, so it was always intended, but it's never been queued. Unlike Requests approval this needs no migration: issue_reports_update already lets Admin/Staff resolve. See the Academy Feature Spec §7, "Three open threads".

The Language toggle is real. It writes users.preferred_language (not null default 'en' check in ('en','fr')), and the Share-feedback screen already reads it to decide whether a testimony lands in content_en or content_fr. What it does not do is translate the interface — next-intl has never been set up in either app, so every label here is a hard-coded English string. The shipped screen says so under the toggle rather than letting someone tap FR and conclude the app is broken. Recommended as its own task next; see the Project Brief's "Known open items".
"Edit profile photo ›" and "Contact information ›" became read-only rows. The columns all exist on users, but email and phone are also sign-in credentials and public.users holds them separately from auth.users — changing one without the other silently desynchronises an account from its login. That needs supabase.auth.updateUser and a re-verification flow, which is its own work. And there is no Supabase Storage bucket on this project, so nothing can produce a profile_photo_url to upload; the avatar falls back to initials, which is the normal case rather than the fallback.
Roles are a read-only list, not a switcher. Third pass to leave the switcher out, and the first to ship something in its place. Listing what someone is needs a query; switching which role a session acts as needs somewhere to persist that and screens whose content varies by it — neither exists, and a dropdown that changed nothing would be worse than an honest list. The staff sub-role is shown when there is one ("Mentor" beats "Staff"), and holiday_maker renders as "Holiday participant".
Log out lives here now. It sat in the app-shell header through the Auth pass as a documented stopgap until this screen existed. It's also rendered on Profile's error state, deliberately: this page is the app's only way out of a session, so someone signed into the wrong account behind a failing profile read would otherwise be stuck.
